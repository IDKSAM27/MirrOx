# scrcpy working:

MediaProjection API (Android 5+)
    Scrcpy uses the MediaProjection API, which is the official way to capture the screen.
    This API provides a virtual display, which Scrcpy captures and encodes.

H.264 / H.265 Hardware Encoding (Faster than Raw Frames)
    Scrcpy does not send raw frames (like screencap does, which is slow).
    Instead, it compresses frames using the phone’s hardware encoder (MediaCodec) before sending them over ADB.

Efficient ADB Data Transfer
    Instead of saving frames as PNG/JPEG, Scrcpy streams an H.264 video over ADB.
    It uses an efficient ADB socket connection to minimize latency.

Decoding & Displaying on PC
    On the PC, Scrcpy decodes the H.264 stream using FFmpeg or OpenGL and renders it in real-time.

------------------------------------------------------------------------------------------
Feature	            screencap (What MirrOx Uses Now)	Scrcpy
------------------------------------------------------------------------------------------
Frame Format	    Raw PNG/JPEG (Large Size)	        H.264 Video Stream (Compressed)
Encoding Method	    None (Huge Data Size)	            Hardware Encoding (Efficient)
Transfer Method	    ADB Pull (Slow)	                    Socket Streaming (Fast)
Latency	            High (~1s delay)	                Low (<50ms)
------------------------------------------------------------------------------------------

# Minicap

* Third-party library (not part of Android's official APIs).
* Uses Android's private SurfaceFlinger API to capture frames.
* Requires root access on some devices.
* Faster than screencap, but less efficient than MediaProjection.
* Used in older screen mirroring tools (before MediaProjection became available).

# MediaProjection API (Official Android API)

* Official Android API (available since Android 5.0 - Lollipop).
* Allows apps to capture the screen without root.
* Used by Scrcpy & other modern mirroring tools.
* More efficient and fully supported by Android.
* Can leverage hardware encoding for low-latency streaming.

------------------------------------------------------------------------------------------------------------
Feature	            Minicap	                                            MediaProjection API
------------------------------------------------------------------------------------------------------------
Official API	    No (Unofficial)	                                    Yes (Google API)
Root Required?	    Some devices need root	                            No root needed
Performance	        Fast, but not as efficient as MediaProjection	    Faster, supports hardware encoding
Compatibility	    Works on most devices (but may break on updates)	Works on all devices Android 5+
Used by Scrcpy?	    No	                                                Yes
------------------------------------------------------------------------------------------------------------

Since Minicap is outdated and sometimes requires root, it's not the best choice.

Instead, we should use the MediaProjection API + H.264 encoding (like Scrcpy).

This will greatly reduce latency and improve performance.

Since we’re launching a .jar, there’s no AndroidManifest, no APK, and no system context, so the Activity fails to launch and causes Aborted.

Since the public MediaProjection constructor is gone, scrcpy doesn’t use it either. Instead, it works directly with the IMediaProjection interface through hidden JNI/NDK calls.

But for your Java-only .jar setup, you can’t directly use IMediaProjection for screen capture unless you fully replace the MediaProjection Java object.

With JNI, we can directly call IMediaProjectionManager.createProjection() using raw Binder transactions from native code, just like scrcpy does.

Step 3: Link the .so Library

fn receive_media_projection:
    Read the binder fd into a buffer.
    Parse commands (u32 values) one by one.
    When finding a BR_TRANSACTION, treat the next bytes as a BinderTransactionData.
    Then after the struct, read 4 bytes = binder handle.
    Return that handle.

fn send_create_projection:
    First fill a TransactionData (all params packed).
    Create a BinderTransactionData that points to this data.
    Then write() the command (BC_TRANSACTION + binder data + arguments) into the Binder device.

tcp_stream:
    Following my agreed-upon "Coordinator-Worker" pattern, tcp_stream module will be a highly focused "Connection Worker." 
    Its only job is to connect to the TCP port that our AdbSession has forwarded.

    It's reusable module that can establish a TCP connection

mux.rs: The Stream Bridge
    The mux.rs module serves as a critical bridge between the raw TCP network stream coming from the Android device and the FFmpeg decoding library. 
    Its primary responsibility is to adapt the unstructured flow of network bytes into a structured, readable source that FFmpeg can understand and process.

    This is necessary because FFmpeg, being a C library at its core, cannot directly consume a Rust TcpStream. 
    It requires a specific C-style interface to request data, which this module provides.

    How It Works
    The process can be broken down into four main steps:

    Server Handshake: Before the video data starts, the scrcpy-server sends a small header containing device metadata (like the device name). The bridge_stream function first reads and processes this header to ensure that only the pure H.264 video stream is passed along to the decoder.

    In-Memory Pipe Creation: The module creates an in-memory pipe, which is essentially a virtual file that exists only in RAM. This pipe has two ends: a pipe_writer and a pipe_reader.

    Dedicated I/O Thread: A new background thread is spawned with the sole purpose of handling network input. This thread continuously reads data from the TcpStream and writes it into the pipe_writer using the highly efficient io::copy function. This decouples network operations from the video decoding loop, preventing network stutters from freezing the application.

    Custom FFmpeg I/O Context: This is the core of the module. It uses low-level functions from the ffmpeg-sys-next crate to manually construct a custom I/O context for FFmpeg.

    It defines a C-compatible read_packet callback function. This is the function that FFmpeg will call whenever it needs more video data.

    When FFmpeg calls this function, it reads the requested data from the pipe_reader and copies it into a buffer provided by FFmpeg.

    Finally, it creates an FFmpeg Input context that is configured to use this custom callback mechanism.

    The final output of the module is a fully prepared ffmpeg::format::context::Input object. This object represents a readable video stream, ready to be passed to the video decoder for processing and rendering.

Insights:

    Raw framebuffer has a header, likely the first 16 bytes (or more) describe image width, height, pixel format, or stride.

        The first 4 bytes = 56, 4, 0, 0 = 0x0458 = 1112 decimal. This often indicates stride or padded row width.

        Next 4 bytes = 96, 9, 0, 0 = 0x0960 = 2400 decimal = height.

        Next 4 bytes = 1, 0, 0, 0 = 1 decimal maybe pixel format code.

    The raw framebuffer data length includes these header bytes, while the GUI is expecting pixel data only.

    The frame size mismatch of 12 bytes relates perfectly to those 16 header bytes plus possibly padding.
